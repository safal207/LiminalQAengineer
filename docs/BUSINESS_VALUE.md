# LiminalQA — Business Value & Positioning

## Одна строка

> **LiminalQA** превращает сырые результаты тестов в готовый диагноз: что сломалось, почему, насколько критично — автоматически, без дежурного инженера.

---

## Проблема которую мы решаем

Каждая команда разработки сталкивается с одним и тем же:

| Симптом | Цена |
|---------|------|
| Тест упал — непонятно: баг или флак? | Инженер тратит 20–40 мин на ручную проверку |
| 300 падений после деплоя | Непонятно с чего начать, смотрят все |
| Флаки-тесты блокируют CI | Команда начинает игнорировать красный CI |
| БД тормозила → упало 15 тестов | Записали 15 багов вместо одного |

**Итог**: команда тратит ~15–20% времени на разбор шума вместо продуктовой работы.

---

## Что даёт LiminalQA — с реальными примерами

### 1. Автоматический триаж (вместо ручного разбора)

Система сама классифицирует каждый тест после каждого прогона:

```
suite/name        verdict      stability  flake   runs
───────────────────────────────────────────────────────
payments/charge   known_issue     0.0%   0.000    9
auth/login        flake          55.6%   0.700    9
health/ping       stable        100.0%   0.000    9
```

**Что это значит для бизнеса:**
- `payments/charge` → `known_issue`: **не надо заводить новый тикет**, проблема уже известна
- `auth/login` → `flake`: **не надо чинить прямо сейчас**, это нестабильный тест, не регрессия
- `health/ping` → `stable`: **можно не смотреть**, всё хорошо

Вместо того чтобы инженер смотрел на 9 упавших тестов, он видит **один экран с диагнозом**.

---

### 2. Приоритизация по важности сигналов (не всё одинаково срочно)

```
Signals ranked by adjusted_importance ↓
  Database  latency= 3200ms  base=1.558  ×ctx=1.122  →  adjusted=1.748
  API       latency=  250ms  base=1.050  ×ctx=1.122  →  adjusted=1.178
  GRPC      latency=   80ms  base=0.864  ×ctx=1.122  →  adjusted=0.969
```

Контекст влияет на оценку:
- **Prod + рабочее время**: множитель ×1.1 — это срочно
- **Dev + ночь + нагрузка 85%**: множитель ×0.4 — это подождёт

**Что это значит для бизнеса:**
Инженер дежурства открывает экран и сразу видит: *«БД на 3.2 секунды — это самое важное прямо сейчас»*. Не надо самому решать с чего начать.

---

### 3. Цепочка причинности (один баг, не пятнадцать)

```
root: Database signal (3200ms)
  depth=0  Database   causal_weight=1.558   → edges: 1
    ↳ Δt=400ms  strength=0.579
    depth=1  GRPC     causal_weight=0.500   → edges: 0
```

БД зависла → через 400мс упал gRPC → упали 3 теста.

**Что это значит для бизнеса:**
- Раньше: 3 отдельных инцидента, 3 разных инженера смотрят
- Теперь: **один корень**, один человек чинит

---

### 4. Новая регрессия — мгновенный алерт и блокировка PR

Когда стабильный тест начинает падать каждый раз:

```
🔴 [CRITICAL] New regression: payments/charge
Test was stable (stability=95%) but last 3 runs all failed.
```

В GitHub PR автоматически появляется комментарий и merge заблокирован:

```markdown
## LiminalQA Triage Report
| Verdict     | Count |
|-------------|-------|
| 🔴 New Bug  | 1     |
| 🟡 Flaky    | 0     |
| 🟢 Stable   | 47    |

**Newly failing stable tests:**
- `payments/charge` — stability was 95%
```

**Что это значит для бизнеса:**
Сломанный код **не попадает в main** без ручного решения инженера. Автоматически, без написания кастомных скриптов.

---

### 5. Шумоподавление (флаки-тесты не засоряют метрики)

```
filtered_latencies_ms: [3200.0, 250.0, 80.0]
```

Если тест упал при нагрузке CPU > 80% — это выброс, он убирается из статистики. Базовая линия считается только по «чистым» прогонам.

**Что это значит для бизнеса:**
- Алерты срабатывают на реальные проблемы, не на флуктуации нагрузки
- Метрики стабильности не врут из-за пиков

---

### 6. Адаптивные таймауты (CI больше не тупит и не флакует)

Система накапливает реальную историю длительности каждого теста и вычисляет безопасный таймаут автоматически:

```
GET /api/timeout-advice/payments/charge

{
  "suggested_timeout_ms": 4850,   ← вот твой таймаут
  "ema_mean_ms":  3200,            ← тест обычно идёт 3.2 сек
  "ema_stddev_ms":  550,           ← разброс ±550 мс
  "confidence":   0.91,            ← уверены на 91% (40 прогонов)
  "is_warmed_up": true
}
```

Формула: `timeout = EMA_mean + 3σ` — покрывает 99.7% нормальных прогонов.
До прогрева (мало данных) возвращает `null` — CI откатывается на статический дефолт.

**Что это значит для бизнеса:**
- Тест с реальным p95 в 3.2 сек больше не флакует из-за `timeout: 3s` в конфиге
- Тест с реальным p95 в 0.5 сек не держит CI на лишние `timeout: 30s`
- Таймауты обновляются автоматически при деградации сервиса

---

### 7. Умный выбор тестов (CI быстрее без потери уверенности)

Система знает, какие тесты стоит запускать на каждом коммите, а какие можно пропустить:

```
GET /api/run-plan/payments

{
  "recommended_to_run":  2,
  "recommended_to_skip": 1,
  "decisions": [
    {
      "name":            "auth/login",
      "action":          "run",
      "reason":          "Флакует (55%) — нужно следить",
      "stability_score": 0.556,
      "verdict":         "flake"
    },
    {
      "name":            "payments/charge",
      "action":          "run",
      "reason":          "known_issue — нужно отслеживать регрессию",
      "stability_score": 0.0,
      "verdict":         "known_issue"
    },
    {
      "name":            "health/ping",
      "action":          "skip",
      "reason":          "Rock-solid: 100% pass за 12 запусков — безопасно пропустить",
      "stability_score": 1.0,
      "verdict":         "stable"
    }
  ]
}
```

Правила принятия решений:
- `always_run` — новый тест, нет истории
- `run` — флак, сломан, или мало прогонов
- `skip` — стабильность ≥ 97% при ≥ 10 прогонах

**Что это значит для бизнеса:**

| Метрика | До | После |
|---------|----|----|
| Тестов в CI прогоне | 500 | ~350 (30% пропущено) |
| Время CI | 12 мин | ~8 мин |
| Пропущенные регрессии | 0 | 0 (нестабильные всегда бегут) |

Скорость растёт — уверенность не падает. Система пропускает только то, что **математически доказало свою надёжность**.

### 8. Decision API — один запрос вместо пяти (для AI-агентов и CI-ботов)

Все предыдущие API давали данные. Этот API даёт **решение**.

Вместо того чтобы агент сам вызывал `/api/triage`, `/api/flake-risk`, `/api/trend`, `/api/timeout-advice` и собирал всё воедино — один запрос отвечает на вопрос «что делать?»:

```
GET /api/decision/payments/charge

{
  "name":               "payments/charge",
  "suite":              "payments",
  "verdict":            "new_bug",
  "confidence":         0.91,
  "severity":           "critical",
  "recommended_action": "block_and_alert",
  "merge_policy":       "block",
  "retry_policy":       "none (real failure — do not retry)",
  "signals": {
    "stability_score":     0.11,
    "flake_probability":   0.05,
    "trend_direction":     "degrading",
    "slope_ms_per_run":    15.2,
    "ema_mean_ms":         3200.0,
    "suggested_timeout_ms": 4850,
    "run_count":           9
  },
  "root_cause_hints": [
    "Test was stable (95% pass rate) but failed in the last 3 consecutive runs — likely a real regression",
    "Duration trending upward at +15.2ms/run — projected +760ms in the next 50 runs"
  ],
  "computed_at": "2025-03-26T12:00:00Z"
}
```

Для PR-бота — suite-level запрос:

```
GET /api/decision/suite/payments

{
  "suite":        "payments",
  "merge_policy": "block",
  "block_reason": "New regression detected in: payments/charge",
  "confidence":   0.87,
  "summary": {
    "total_tests":       3,
    "blocking_failures": 1,
    "flaky_tests":       1,
    "stable_tests":      1,
    "degrading_tests":   1,
    "skippable_tests":   1
  },
  "action_items": [
    {
      "name":     "payments/charge",
      "action":   "block_and_alert",
      "reason":   "New regression — was 95% stable",
      "severity": "critical"
    },
    {
      "name":     "auth/login",
      "action":   "retry_with_backoff",
      "reason":   "Oscillates 55% pass — timing/env sensitive",
      "severity": "high"
    }
  ]
}
```

**Словарь `recommended_action` (замкнутый, без магических строк):**

| Значение | Что делать |
|----------|-----------|
| `run` | Запустить нормально |
| `retry_immediately` | Ретрай один раз — вероятно transient |
| `retry_with_backoff` | Высокий риск флака — exponential backoff |
| `investigate` | Стабильное падение — эскалировать инженеру |
| `monitor_trend` | Стабилен, но деградирует — наблюдать |
| `skip` | Надёжный — безопасно пропустить |
| `block_and_alert` | Новая регрессия — стоп пайплайн |
| `observe_only` | Мало данных — наблюдать без действий |

**Как это использует AI-агент:**

```python
# OpenAI / Anthropic tool calling
decision = call_tool("get_test_decision", suite="payments", test="charge")

if decision["merge_policy"] == "block":
    block_pr(reason=decision["block_reason"])
elif decision["merge_policy"] == "allow_with_warning":
    add_pr_annotation(decision["root_cause_hints"])

if decision["recommended_action"] == "retry_with_backoff":
    schedule_retry(policy=decision["retry_policy"])
```

**Что это значит для бизнеса:**
- GitHub Action бот: один API-вызов → блокировать PR или пропустить
- AI coding agent (Claude, Copilot): понимает качество тестов без написания логики анализа
- CLI: `limctl decision payments/charge` — мгновенный диагноз в терминале
- Любая интеграция: одна схема, закрытый словарь, предсказуемый формат

## Кому это нужно

| Роль | Что получает |
|------|-------------|
| **Дежурный инженер** | Открывает один экран — видит что чинить и в каком порядке |
| **Lead / TL** | Еженедельный Issue с топ-флаками, тренд стабильности |
| **QA инженер** | Триаж уже сделан, не надо вручную сортировать 200 падений |
| **Разработчик** | PR заблокирован с объяснением причины, не нужно гадать |
| **CTO / VP Eng** | Дашборд: % стабильных тестов, количество новых регрессий в неделю |

## Интеграция — одна строка в CI

Добавить в `.github/workflows/`:

```yaml
- name: Ingest test results
  run: |
    curl -X POST "$LIMINALQA_URL/ingest/batch" \
      -H "Authorization: Bearer $LIMINALQA_TOKEN" \
      -d @test-results.json
```

Всё остальное — автоматически. Никакой конфигурации агентов, никаких дополнительных сервисов.

Готовые шаблоны для GitHub Actions, GitLab CI, systemd, Kubernetes — в репозитории.

## Ключевые метрики (что можно продемонстрировать)

| Метрика | До | После |
|---------|----|-------|
| Время на ручной триаж 300 падений | ~3 часа | ~5 минут |
| Ложные алерты (флаки как баги) | 30–40% | <5% |
| Время до обнаружения регрессии | Следующий стендап | <2 минуты |
| Количество «а это известный флак» тикетов | Много | 0 (система знает сама) |
| Таймауты — откуда берутся | Из головы / интуиция | EMA mean + 3σ по реальной истории |
| Тестов запускается в CI | 100% | ~70% (стабильные пропускаются) |
| Время CI | baseline | −20–30% без потери уверенности |

## Конкуренты и дифференциация

| Инструмент | Что умеет | Чего не умеет |
|------------|-----------|---------------|
| Allure Report | Красивые отчёты | Нет авто-триажа, нет алертов |
| DataDog Synthetic | Мониторинг | Нет анализа тестов, дорого |
| BuildKite / CircleCI | CI/CD | Только run/fail, нет диагностики |
| **LiminalQA** | Триаж + причинность + алерты | **Это и есть ниша** |

**Ниша**: между «CI показал красный» и «инженер понял что делать» — сейчас там пустота. LiminalQA её заполняет.

## Техническая уникальность (для технической аудитории)

- **Би-темпоральная БД**: `valid_time` (когда случилось) vs `tx_time` (когда узнали) — можно восстановить «что система знала в момент X»
- **Встроенная БД (sled)**: нет внешних зависимостей, одним бинарником
- **Причинность с затуханием**: `strength = importance × exp(−Δt / 1000ms)` — математически обоснованная близость событий
- **Контекстный множитель**: prod/staging/dev × business-hours/night × low/high-load — одна формула для всех окружений
- **EMA-базелайн**: онлайн-алгоритм, α = 2/(period+1), отслеживает среднее и дисперсию без хранения всей истории
- **Адаптивный таймаут**: `mean + 3σ` по EMA — обновляется на каждом прогоне, требует нулевой конфигурации
- **Умный выбор тестов**: математически обоснованный skip — только тесты с ≥97% стабильностью за ≥10 прогонов
