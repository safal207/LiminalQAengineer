# LiminalQA — Business Value & Positioning

## Одна строка

> **LiminalQA** превращает сырые результаты тестов в готовый диагноз: что сломалось, почему, насколько критично — автоматически, без дежурного инженера.

---

## Проблема которую мы решаем

Каждая команда разработки сталкивается с одним и тем же:

| Симптом | Цена |
|---------|------|
| Тест упал — непонятно: баг или флак? | Инженер тратит 20–40 мин на ручную проверку |
| 300 падений после деплоя | Непонятно с чего начать, смотрят все |
| Флаки-тесты блокируют CI | Команда начинает игнорировать красный CI |
| БД тормозила → упало 15 тестов | Записали 15 багов вместо одного |

**Итог**: команда тратит ~15–20% времени на разбор шума вместо продуктовой работы.

---

## Что даёт LiminalQA — с реальными примерами

### 1. Автоматический триаж (вместо ручного разбора)

Система сама классифицирует каждый тест после каждого прогона:

```
suite/name        verdict      stability  flake   runs
───────────────────────────────────────────────────────
payments/charge   known_issue     0.0%   0.000    9
auth/login        flake          55.6%   0.700    9
health/ping       stable        100.0%   0.000    9
```

**Что это значит для бизнеса:**
- `payments/charge` → `known_issue`: **не надо заводить новый тикет**, проблема уже известна
- `auth/login` → `flake`: **не надо чинить прямо сейчас**, это нестабильный тест, не регрессия
- `health/ping` → `stable`: **можно не смотреть**, всё хорошо

Вместо того чтобы инженер смотрел на 9 упавших тестов, он видит **один экран с диагнозом**.

---

### 2. Приоритизация по важности сигналов (не всё одинаково срочно)

```
Signals ranked by adjusted_importance ↓
  Database  latency= 3200ms  base=1.558  ×ctx=1.122  →  adjusted=1.748
  API       latency=  250ms  base=1.050  ×ctx=1.122  →  adjusted=1.178
  GRPC      latency=   80ms  base=0.864  ×ctx=1.122  →  adjusted=0.969
```

Контекст влияет на оценку:
- **Prod + рабочее время**: множитель ×1.1 — это срочно
- **Dev + ночь + нагрузка 85%**: множитель ×0.4 — это подождёт

**Что это значит для бизнеса:**
Инженер дежурства открывает экран и сразу видит: *«БД на 3.2 секунды — это самое важное прямо сейчас»*. Не надо самому решать с чего начать.

---

### 3. Цепочка причинности (один баг, не пятнадцать)

```
root: Database signal (3200ms)
  depth=0  Database   causal_weight=1.558   → edges: 1
    ↳ Δt=400ms  strength=0.579
    depth=1  GRPC     causal_weight=0.500   → edges: 0
```

БД зависла → через 400мс упал gRPC → упали 3 теста.

**Что это значит для бизнеса:**
- Раньше: 3 отдельных инцидента, 3 разных инженера смотрят
- Теперь: **один корень**, один человек чинит

---

### 4. Новая регрессия — мгновенный алерт и блокировка PR

Когда стабильный тест начинает падать каждый раз:

```
🔴 [CRITICAL] New regression: payments/charge
Test was stable (stability=95%) but last 3 runs all failed.
```

В GitHub PR автоматически появляется комментарий и merge заблокирован:

```markdown
## LiminalQA Triage Report
| Verdict     | Count |
|-------------|-------|
| 🔴 New Bug  | 1     |
| 🟡 Flaky    | 0     |
| 🟢 Stable   | 47    |

**Newly failing stable tests:**
- `payments/charge` — stability was 95%
```

**Что это значит для бизнеса:**
Сломанный код **не попадает в main** без ручного решения инженера. Автоматически, без написания кастомных скриптов.

---

### 5. Шумоподавление (флаки-тесты не засоряют метрики)

```
filtered_latencies_ms: [3200.0, 250.0, 80.0]
```

Если тест упал при нагрузке CPU > 80% — это выброс, он убирается из статистики. Базовая линия считается только по «чистым» прогонам.

**Что это значит для бизнеса:**
- Алерты срабатывают на реальные проблемы, не на флуктуации нагрузки
- Метрики стабильности не врут из-за пиков

---

## Кому это нужно

| Роль | Что получает |
|------|-------------|
| **Дежурный инженер** | Открывает один экран — видит что чинить и в каком порядке |
| **Lead / TL** | Еженедельный Issue с топ-флаками, тренд стабильности |
| **QA инженер** | Триаж уже сделан, не надо вручную сортировать 200 падений |
| **Разработчик** | PR заблокирован с объяснением причины, не нужно гадать |
| **CTO / VP Eng** | Дашборд: % стабильных тестов, количество новых регрессий в неделю |

## Интеграция — одна строка в CI

Добавить в `.github/workflows/`:

```yaml
- name: Ingest test results
  run: |
    curl -X POST "$LIMINALQA_URL/ingest/batch" \
      -H "Authorization: Bearer $LIMINALQA_TOKEN" \
      -d @test-results.json
```

Всё остальное — автоматически. Никакой конфигурации агентов, никаких дополнительных сервисов.

Готовые шаблоны для GitHub Actions, GitLab CI, systemd, Kubernetes — в репозитории.

## Ключевые метрики (что можно продемонстрировать)

| Метрика | До | После |
|---------|----|-------|
| Время на ручной триаж 300 падений | ~3 часа | ~5 минут |
| Ложные алерты (флаки как баги) | 30–40% | <5% |
| Время до обнаружения регрессии | Следующий стендап | <2 минуты |
| Количество «а это известный флак» тикетов | Много | 0 (система знает сама) |

## Конкуренты и дифференциация

| Инструмент | Что умеет | Чего не умеет |
|------------|-----------|---------------|
| Allure Report | Красивые отчёты | Нет авто-триажа, нет алертов |
| DataDog Synthetic | Мониторинг | Нет анализа тестов, дорого |
| BuildKite / CircleCI | CI/CD | Только run/fail, нет диагностики |
| **LiminalQA** | Триаж + причинность + алерты | **Это и есть ниша** |

**Ниша**: между «CI показал красный» и «инженер понял что делать» — сейчас там пустота. LiminalQA её заполняет.

## Техническая уникальность (для технической аудитории)

- **Би-темпоральная БД**: `valid_time` (когда случилось) vs `tx_time` (когда узнали) — можно восстановить «что система знала в момент X»
- **Встроенная БД (sled)**: нет внешних зависимостей, одним бинарником
- **Причинность с затуханием**: `strength = importance × exp(−Δt / 1000ms)` — математически обоснованная близость событий
- **Контекстный множитель**: prod/staging/dev × business-hours/night × low/high-load — одна формула для всех окружений
